# 警察抓小偷（Cocos）游戏架构规划

## Summary
- 基于 Cocos Creator（TypeScript）实现益智解谜游戏“警察抓小偷”
- 棋盘为可变尺寸的正方形网格；包含建筑（固定障碍）、小偷（单格起点）、警察（玩家放置的单格障碍）
- 目标：玩家通过摆放警察方块，使“小偷通过四向走格”无法从当前连通区域到达棋盘外（不存在逃脱路径）
- 架构目标：核心规则与关卡数据平台无关；渲染/UI 与平台能力（存储/分享/广告等）解耦，便于发布到 Web、微信小游戏、抖音小游戏、鸿蒙等

## Current State Analysis
- 仓库当前仅包含 [README.md](file:///workspace/README.md)，没有现成 Cocos 项目结构、脚本或资源
- 因此需要从 0 初始化 Cocos Creator 项目并建立脚本/资源/构建模板的目录约定

## Game Definition（决策已锁定）
- **棋盘连通**：四向（上/下/左/右）移动
- **逃脱判定**：若存在从小偷位置出发，沿“可通行格”四向连通，到达任意边界并可继续走出棋盘（等价于可到达任意边界可通行格）则视为存在逃脱路径
- **建筑**：关卡预置，建筑所在格不可通行
- **警察**：玩家放置，警察所在格不可通行（仅占一格）
- **关卡**：预设关卡（配置驱动），后续可扩展编辑器与每日挑战

## Proposed Changes

### 1) 项目与目录结构（Cocos Creator）
目标：明确“核心逻辑 / 引擎适配 / 平台适配 / 资源数据”分层，减少跨平台时的改动范围。

- 新建 Cocos Creator 项目（Creator 3.x，TypeScript）
- 约定目录（后续实现按此创建）：
  - `/assets/scripts/core/`
    - 纯规则与数据结构（不依赖 cc.*），可在任意平台复用
  - `/assets/scripts/game/`
    - 游戏用例层：关卡装载、玩家操作、胜负判定、撤销重做、存档
  - `/assets/scripts/view/`
    - 视图层：网格渲染、拖拽放置、动效、UI 面板
  - `/assets/scripts/platform/`
    - 平台能力抽象与各平台实现（微信/抖音/鸿蒙/原生/Web）
  - `/assets/resources/levels/`
    - 关卡 JSON（或其他可序列化格式），运行时读取
  - `/assets/resources/config/`
    - 全局配置（警察皮肤/建筑皮肤、音效开关默认值、语言等）
  - `/assets/scenes/`
    - `boot.scene`（初始化、平台注入、资源预加载）
    - `levelSelect.scene`（选关）
    - `gameplay.scene`（主玩法）
  - `/assets/prefabs/`
    - `Cell.prefab`、`PoliceTile.prefab`、UI 组件等

### 2) 核心规则层（core：纯 TypeScript）
目标：将“棋盘、关卡、判定、寻路”做成纯数据与算法，保证可测试、可复用、可移植。

- 关键模块（建议文件）：
  - `core/types.ts`
    - `Vec2`、`CellType`、`PieceType` 等基础类型
  - `core/board.ts`
    - `BoardState`：width/height、建筑集合、警察集合、小偷位置
    - 查询 API：`isInside(pos)`、`isBlocked(pos)`、`neighbors4(pos)`
  - `core/level.ts`
    - `LevelConfig`：关卡配置结构（见“关卡数据规范”）
    - `LevelLoader`：将 JSON 转换为 `BoardState` 初始状态与警察库存
  - `core/escape.ts`
    - `hasEscapePath(board: BoardState): boolean`
      - 从小偷位置 BFS/FloodFill，走访所有可通行格
      - 若访问到任意“边界可通行格”则返回 true（存在逃脱路径）
  - `core/validation.ts`
    - 关卡静态校验（坐标越界、重叠、无效库存等）

#### 关卡数据规范（LevelConfig）
目标：支持多尺寸方形棋盘、预置建筑与小偷位置、关卡提供的警察库存、可扩展元数据。

- 建议 JSON 结构（示意）：
  - `id: string`
  - `size: number`（正方形边长；也可扩展为 `width/height`）
  - `thief: { x: number, y: number }`
  - `buildings: Array<{ x: number, y: number, variant?: string }>`
  - `policePool: Array<{ variant: string, count: number }>`
  - `constraints?: { maxPoliceUsed?: number }`
  - `meta?: { title?: string, difficulty?: number }`

### 3) 游戏用例层（game：状态机 + 操作系统）
目标：把“玩家放置—判定—胜利/失败—撤销/重做—存档”做成清晰的状态机，避免 UI 直接改核心状态。

- 核心对象：
  - `GameSession`
    - 持有 `BoardState` 当前快照、警察库存、已放置警察列表
    - 提供原子操作：
      - `tryPlacePolice(pos, variant)`：检查是否空格/是否有库存
      - `removePolice(pos)`
      - `checkWin()`：`!hasEscapePath(board)` 且满足可选约束（如最大使用数）
  - `Command` / `History`
    - 对放置/移除封装命令，实现撤销/重做
  - `SaveService`
    - 保存：已通关关卡、当前关卡进度（可选）、设置项
    - 通过 `platform` 层落地到本地存储（微信/抖音用各自 API，其它用 localStorage/文件）

### 4) 视图层（view：渲染与交互）
目标：视图只订阅/渲染 `GameSession`，所有规则都走 game/core；便于替换 UI 方案与适配不同屏幕。

- 关键组件职责：
  - `BoardView`
    - 根据 `BoardState` 生成/复用 Cell 节点（对象池）
    - 坐标映射：格子坐标 ↔ 世界坐标（适配不同尺寸与分辨率）
  - `PlacementUI`
    - 警察库存面板（variant + count）
    - 拖拽/点击放置：落点映射到格子，调用 `GameSession.tryPlacePolice`
  - `ResultPanel`
    - 胜利：下一关/重开/返回
    - 失败：提示“存在逃脱路径”并高亮边界连通区域（可选增强）

### 5) 平台层（platform：能力抽象 + 多实现）
目标：统一暴露存储/埋点/广告/分享/振动/隐私弹窗等能力；各平台通过实现类接入，业务层不直接调用平台 SDK。

- 接口定义（建议）：
  - `IPlatformBridge`
    - `getPlatform(): 'web' | 'wechat' | 'douyin' | 'harmony' | 'native'`
    - `storageGet/Set`
    - `showToast`
    - `vibrate`
    - `share`（可选）
    - `showRewardedAd`（可选）
    - `logEvent`（可选）
- 选择策略：
  - Boot 场景根据运行环境注入 bridge（例如通过 Cocos 的平台宏/运行时判断）
  - game 层依赖接口，不依赖具体实现

### 6) 多平台发布策略（微信/抖音/鸿蒙等）
目标：把“构建产物差异”限制在构建配置与 platform 实现中，核心玩法与资源保持一致。

- 输出目标与对应策略（规划层面）：
  - Web（调试与发布）：Creator Web 构建
  - 微信小游戏：使用 Creator 的微信小游戏构建目标 + `platform/wechat/*` 适配
  - 抖音小游戏：使用 Creator 的字节跳动小游戏构建目标 + `platform/douyin/*` 适配
  - 鸿蒙：
    - 优先方案：Creator 原生构建 + 鸿蒙打包模板（将平台差异限制在 `platform/harmony/*` 与构建模板）
    - 若需要接入系统能力（登录/支付/广告等），仍通过 `IPlatformBridge` 对接
- 资源与关卡：
  - 关卡 JSON 使用 `resources` 目录，所有平台同一套
  - 音频/图集按 Creator 标准资源管理，避免平台特性资源格式

## Assumptions & Decisions
- 关卡为“正方形棋盘多尺寸”，但单关内 `size` 固定
- 小偷不需要逐步行动演示；核心是“放置后判定是否存在逃脱路径”
- 建筑与警察都只阻挡其所在格；“不同方块”优先作为 variant/皮肤字段处理
- 初期不引入第三方状态管理/测试框架，避免平台兼容与依赖风险；核心逻辑保持纯 TypeScript 便于后续补测
